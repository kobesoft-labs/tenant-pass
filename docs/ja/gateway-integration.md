# ゲートウェイ連携

[English](../en/gateway-integration.md)

ゲートウェイは、どのリクエストにパスを与えるべきかを判断するコンポーネントです。**tenant-pass のセキュリティは、この判断に依存しています。** まず [脅威モデル](threat-model.md#ゲートウェイに関する残存リスク) をお読みください。

## ルール

> テナント T とアプリケーション A に対するパスに署名してよいのは、そのリクエストがテナント T に対して認可されていることをゲートウェイ自身が検証し（T に属する認証済みのユーザーセッション、または T に対する署名付きのジョブ認可）、かつゲートウェイがそのリクエストを A に転送する場合 **だけ** です。

パスはルーティングのヒントではありません。「いま、テナント T の認証情報を取得してよい」という権限（ケイパビリティ）です。

## すべきこと

- 署名する **前に** エンドユーザーのセッション（Cookie、OIDC トークン、mTLS）を認証し、そのセッションが要求されたホストのテナントに属していることを確認してください。テナント B の有効なセッションから、テナント A のホストのパスが生成されてはなりません。
- 正規化済みのホスト名（小文字、ポートなし、末尾のドットなし、IDN は A ラベル）を使ってください。`Host` ヘッダーを、正規化もテナントドメインの一覧との照合もせずにそのままコピーしてはいけません。
- `aud` には、実際にリクエストを受け取るアプリケーション（ルーティング先のアップストリーム）を設定してください。リクエストから得た値を設定してはいけません。
- パスは短命にしてください。リクエストハンドラーには `exp = iat + 30s` で十分です。
- `jti` は CSPRNG から生成し（16 バイト、base64url）、ログに記録して、監査ログと突き合わせられるようにしてください。
- トークンは、クライアントが設定できないリクエストヘッダー（たとえば `Tenant-Pass`）でアプリケーションに渡してください。その前に、エッジで **クライアントからのリクエストに含まれるそのヘッダーを取り除いてください**。
- 秘密鍵はゲートウェイにのみ置き、ゲートウェイのプロセスだけが読み取れるファイル、または HSM/KMS に保管してください。
- ゲートウェイのデプロイごとに 1 つの鍵を使うことを推奨します（環境/クラスターごとに `kid` を分ける）。そうすれば、1 つの鍵だけを失効させられます。

## してはいけないこと

- 認証のないルート（ログイン、サインアップ、パスワードリセット、ヘルスチェック、静的アセット、公開 API、サードパーティからの Webhook）に対してパスに署名しないでください。
- アプリケーションがネットワーク内部からゲートウェイの署名経路に到達できるようにしないでください。任意の `Host` ヘッダーを付けて「ゲートウェイ経由で」自分自身にリクエストを送れるアプリケーションは、任意のテナントのパスを入手できてしまいます。ネットワークレベルでブロックするか、ゲートウェイが公開リスナーに届いたトラフィックに対してのみ署名するようにしてください。
- テナントディレクトリが未検証とみなしているホスト名（たとえば所有権が確認されていないカスタムドメイン）に対してパスに署名しないでください。
- ゲートウェイ鍵を他の用途に再利用しないでください。暗黙のアサーションによって PASETO 内でのプロトコル間の混同は防げますが、それでも鍵を分けておくほうが、安全性を検討する上で単純です。

## バックグラウンドジョブ

エンドユーザーを起点としないリクエスト（キュー、cron、マイグレーション）には、ゲートウェイがチェックすべきセッションがありません。選択肢を、望ましい順に示します。

1. **エンキュー時のパスだけでは不十分です。** パスの寿命は数秒で、ジョブはその後に実行されます。ジョブのために `max_ttl` を延ばさないでください。
2. 利用者が運用する、アプリケーションとは別の **ジョブ認可サービス** が、自身が認可したジョブに対してパスに署名します（たとえば、どのテナントに定期レポートが予定されているかを把握しているスケジューラー）。これを独自の `kid` を持つ別のゲートウェイ鍵として設定すると、そのパスを区別でき、その鍵を独立して失効させられます。
3. `max_tenants_per_minute` を低くした、別のアプリケーション ID（`aud`）の中でジョブを実行します。

## 鍵のローテーション

1. 新しい鍵を生成します: `tenant-pass gen-gateway-key -private gw-2026-12.key -public gw-2026-12.pub`。
2. 公開鍵を（新しい `id` で）すべての tenant-pass レプリカの `gateway_keys` に追加し、展開します。
3. ゲートウェイを、新しい鍵と `kid` で署名するように切り替えます。
4. `pass.max_ttl` が経過した後、古い鍵を `gateway_keys` から削除し、再度展開します。

## 実装の検証

署名の実装は、[テストベクター](pass-format.md#テストベクター) をバイト単位で完全に再現しなければなりません。稼働中の tenant-pass に対して `curl` でパスを確認することもできます（[README](../../README.ja.md#クイックスタート) を参照）。また、ローカルでデコードすることもできます。

```sh
tenant-pass sign-pass -key gw.key -kid gw1 -aud billing -host acme.example.com   # reference output
```

## 例: forward-auth

多くのプロキシ（Caddy の `forward_auth`、nginx の `auth_request`、Traefik ForwardAuth、Envoy の `ext_authz`）は、転送の前に認可サービスを呼び出せます。その場合、小さなサービスで次のことを行えます。

1. 元のリクエストのヘッダーを受け取る。
2. セッションを検証し、テナントに対応付ける。
3. 要求されたホストがそのテナントに属することを確認する。
4. `Tenant-Pass: <pass>` レスポンスヘッダーを付けて `200` を返す。プロキシはこれをアップストリームへのリクエストにコピーする。
5. それ以外の場合は `401`/`403` を返す（パスは決して返さない）。

このようなサービスが tenant-pass から必要とするのは、Go の `pass` パッケージ（`pass.Signer`）だけです。
