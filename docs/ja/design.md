# 設計

[English](../en/design.md)

このドキュメントでは、tenant-pass がどのように動作するのか、そしてなぜそのように作られているのかを説明します。何を防ぎ、何を防がないのかについては [脅威モデル](threat-model.md) を参照してください。

## コンポーネント

| コンポーネント | 保持するもの | 役割 |
| --- | --- | --- |
| **ゲートウェイ**（利用者のプロキシの背後に置く `tenant-pass-gateway`、または利用者独自のコンポーネント） | ゲートウェイの Ed25519 **秘密** 鍵 | エンドユーザーのセッションをテナントに対して認証し、テナントと転送先アプリケーションを記載した短命のパスに署名します。[gateway.md](gateway.md) を参照してください。 |
| **ジョブ発行者**（任意、利用者側で用意: スケジューラー） | 発行者の Ed25519 秘密鍵 | どのリクエストからも開始されないスケジュールされた処理のために、ジョブチケットに署名します。[jobs.md](jobs.md) を参照してください。 |
| **KMS**（任意: Vault / OpenBao） | ローテーション鍵と署名鍵 | HMAC と署名を計算するため、鍵が KMS の外に出ることはありません。[kms.md](kms.md) を参照してください。 |
| **アプリケーション**（利用者側で用意） | 自身のアプリトークン（とクライアント証明書のいずれか、または両方） | リクエストとパスを受け取り、パスをテナントの認証情報と交換し、テナントのデータベースに接続します。 |
| **tenant-pass** | ゲートウェイの **公開** 鍵、アプリトークンのハッシュ、ローテーション鍵、ストアの管理者認証情報 | アプリとパスを検証し、テナントを解決し、認証情報を設定して返します。 |
| **ディレクトリ**（静的な設定、または利用者側の PostgreSQL/MySQL） | テナント → ノード、アカウント、有効/無効、許可されたアプリ | どのアカウントがどのテナントに属するかについての信頼できる情報源です。 |
| **ストア**（PostgreSQL、MySQL、Redis） | テナントのアカウント | tenant-pass が設定したパスワードを強制します。 |

ゲートウェイの秘密鍵とローテーション鍵が同じ場所に置かれることはありません。ゲートウェイはパスに署名できますがパスワードは導出できず、tenant-pass はパスワードを導出できますがパスには署名できません。アプリケーションはどちらも持ちません。

## バックグラウンドジョブ

パスの寿命は数秒です。後から実行される処理は **ジョブチケット** を使います。ジョブチケットは、別の暗黙のアサーション（`tenant-pass/v1/job`）を持ち、常にテナント ID を記載し、最大で `job_tickets.max_ttl` まで有効な PASETO トークンです。tenant-pass はパスと引き換えにジョブチケットを発行し（`POST /v1/job-tickets`。アプリケーションごとのオプトイン）、また利用者が運用する信頼された発行者（スケジューラー）からのチケットも受け付けます。引き換えでは、パスと同じディレクトリとストアのチェックが行われ、レート制限は別枠です。詳細: [jobs.md](jobs.md)。

## リクエストフロー

```
Application                         tenant-pass                                Directory        Store
    │ POST /v1/credentials               │                                          │               │
    │ Authorization: Bearer tpa_…        │                                          │               │
    │ {"pass": "v4.public.…"}  ─────────▶│ 1 method / path / content type           │               │
    │                                    │ 2 authenticate app → "billing"           │               │
    │                                    │ 3 parse body strictly (≤ 4 KiB)          │               │
    │                                    │ 4 verify pass: key ID → gateway key,     │               │
    │                                    │   signature, claims, lifetime,           │               │
    │                                    │   aud == "billing"                       │               │
    │                                    │ 5 distinct-tenant rate limit             │               │
    │                                    │ 6 lookup(host or tenant, app) ──────────▶│               │
    │                                    │   ◀── tenant_id, node, account, enabled  │               │
    │                                    │ 7 store.Issue(account) ─────────────────────────────────▶│
    │                                    │   lock → safety checks → read state →    │               │
    │                                    │   plan (forward-only) → write if needed  │               │
    │ ◀───────── credential ─────────────│ audit log (never secrets)                │               │
```

すべてのステップはフェイルクローズします。クライアントが受け取るのは固定のエラーコード（`invalid_pass`、`denied` など）だけで、理由は返されません。理由は監査ログに記録されます。

## パス

パス（pass）は [PASETO v4.public](https://github.com/paseto-standard/paseto-spec) トークン（Ed25519）です。完全な仕様は [pass-format.md](pass-format.md) にあります。主な設計判断は次のとおりです。

- **JWT ではなく PASETO。** v4.public のアルゴリズムはただ 1 つです。混乱の元になる `alg` ヘッダーも、`none` も、RSA/HMAC の鍵の取り違えもありません。tenant-pass は `v4.public.` のみを受け付けます。
- **暗黙のアサーション（implicit assertion）`tenant-pass/v1/pass`。** これは署名には含まれますが、送信はされません。同じ鍵で別の目的（別の製品、tenant-pass の別バージョン）のために署名されたトークンは、パスとして受け付けられません。
- **フッターでの鍵 ID は必須。** フッターによってゲートウェイ鍵が選ばれるため、ゲートウェイ鍵のローテーションや複数のゲートウェイの運用が可能になります。フッターは署名によって認証されます。検証前には、鍵の選択にのみ使われます。
- **厳格なクレーム。** クレームは `aud`、`jti`、`iat`、`exp` と、`host` / `tenant` のいずれか 1 つで、それ以外はありません。未知のクレームや重複したクレームは拒否されます（JSON キーの重複は、言語間でパーサーの解釈が食い違う原因としてよく知られています）。時刻は秒単位（小数なし）の RFC 3339 UTC 形式で、各時点の文字列表現は一意になります。
- **短い寿命。** `exp - iat` は最大で `pass.max_ttl`（デフォルト 60 秒、上限 5 分）です。
- **正規化済みのホスト名のみ。** tenant-pass はホスト名を正規化しません。ポートや末尾のドットを含まない小文字の ASCII 以外はすべて拒否します。正規化を 2 か所（ゲートウェイと tenant-pass）で行うと、食い違いを招くからです。
- **リプレイキャッシュなし。** パスはその有効期間内であれば複数回提示できます（リクエストハンドラーが再接続する必要がある場合など）。パスは 1 つのアプリケーションに束縛され、数秒で失効するため、他者によるリプレイは不可能であり、同じアプリケーションによるリプレイでは、すでに持っている以上のものは何も得られません。

## パスワードとウィンドウ

tenant-pass は、共有状態を持たない同一のレプリカを複数実行する構成で動作します。同じアカウントについて同時に問い合わせを受けた 2 つのレプリカは、同じパスワードを返さなければなりません。tenant-pass は協調する代わりに、すべてのレプリカが同じ入力からパスワードを導出します。

```
password(n) = base64url(HMAC-SHA256(K, "tenant-pass/v1/password" || LP(store) || LP(node) || LP(account) || LP(key ID) || BE64(W) || BE64(n)))
```

- `n` は **ウィンドウ** 番号です。ウィンドウの長さは `rotation.window`（デフォルト 15 分）です。各アカウントのウィンドウは (store, node, account) のハッシュから導出したオフセットだけずらされるため、すべてのアカウントが同時にローテーションされることはありません。
- `K` は、ウィンドウ `n` の開始時点で有効なローテーション鍵です。鍵には `not_before` 時刻があるため、新しい鍵を前もって配布しておき、すべてのレプリカが同じウィンドウで切り替えることができます。
- 出力は PRF による 256 ビットの値で、ランダムなパスワードと同等の強度を持ちます。

正確な仕様とテストベクター（独立した Python 実装で生成したもの）は [derivation.md](derivation.md) にあります。

### 更新

ウィンドウ `n` の残り時間が `rotation.renew_before`（デフォルト 5 分）を下回ると、tenant-pass はすでにウィンドウ `n+1` を払い出します。そのため、クライアントが受け取った時点で、どの認証情報も少なくとも `renew_before` の間は有効です。レスポンスには、クライアントがいつ更新すべきか（`refresh_at = End(n) − renew_before`）が含まれます。

### 前進のみ（forward-only）

時計はずれるものです。時計がわずかに遅れているレプリカが、アカウントを古いウィンドウに戻し、すでに新しいパスワードを受け取ったクライアントを壊すようなことがあってはなりません。tenant-pass はアカウントの現在の状態を *ロックを取得した状態で* 読み取り、次のルールを適用します。

- すでに目標のウィンドウにある → それを再利用します（書き込みなし）。
- すでに次のウィンドウにある（別のレプリカの時計がわずかに進んでいる）→ そちらを払い出します。決して戻しません。
- より古い、不明、または管理対象外の状態 → 目標のウィンドウを書き込みます。
- 2 ウィンドウ以上先にある → 管理対象外として扱い、上書きします。放置すると、パスワードがはるか未来まで有効なままになってしまいます。

最後のルールが安全なのは、別のガードがあるからです。**書き込みの前に、各レプリカは自分の時計とストアサーバーの時計を比較します**（PostgreSQL の `clock_timestamp()`、MySQL の `NOW(6)`、Redis の `TIME`。同じラウンドトリップ内で読み取ります）。差が `rotation.max_clock_skew`（デフォルト 10 秒）を超えると、そのレプリカは `clock_skew` で拒否します。したがって、時計が飛んだレプリカ（NTP の障害、VM スナップショットからの復元など）は、アカウントを未来にも過去にも動かせません。書き込むのは、データベースと時刻が一致しているレプリカだけです。

tenant-pass は何も保存せずに自身が設定した状態を認識します。PostgreSQL では `VALID UNTIL` の境界値が正確に一致するかどうかで、MySQL と Redis では候補となるハッシュを再計算して比較することで判断します。

## ストアのモデル

### ハードな有効期限: PostgreSQL

ロールが持てるパスワードは 1 つです。tenant-pass は `PASSWORD '<SCRAM verifier>' VALID UNTIL '<End(n)>'` を設定します。`End(n)` を過ぎると、tenant-pass が利用できない状態でも、PostgreSQL 自身がそのパスワードを拒否します。既存の接続は、パスワードの変更や失効の影響を受けません。

パスワードが 1 つしかないため、`n` から `n+1` への切り替え（更新フェーズの開始時）によって、*新規* 接続に対する `n` は即座に無効になります。クライアントは認証失敗（SQLSTATE `28P01`）時に、新しい認証情報を取得して 1 回リトライしなければなりません。[client-integration.md](client-integration.md) を参照してください。

### ソフトな有効期限: MySQL と Redis

どちらにもパスワードの有効期限はありませんが、どちらも 2 つのパスワードを同時に保持できます（MySQL のデュアルパスワード。Redis の ACL ユーザーは複数のパスワードを持てます）。tenant-pass は次のように保持します。

- 通常フェーズ: ウィンドウ `n` のパスワード
- 更新フェーズ: ウィンドウ `n` と `n+1`

更新中は新旧どちらの認証情報も使えるため、認証失敗の競合は発生しません。バックグラウンドの **スイーパー**（`rotation.sweep_interval` ごと、デフォルト 30 秒、ジッターあり）が、ウィンドウが終了したパスワードと、tenant-pass が導出していないパスワードを削除します。1 ウィンドウの間まったく要求されなかったアカウントには、最終的に使えるパスワードが 1 つも残りません。したがって、パスワードは `expires_at` を最大でスイープ間隔 1 回分（tenant-pass が停止している場合は、さらにその停止時間分）長く生き残ることがあります。

## アカウントの安全性チェック

tenant-pass はパスワードをリセットします。誤ったアカウントを指してしまうと危険です。そのため、ディレクトリに加えて、各ストアは書き込みと同じロックの下でアカウント自体をチェックします。

| | PostgreSQL | MySQL | Redis |
| --- | --- | --- | --- |
| 名前が `account_pattern`（アンカー付き正規表現）に一致する | ✓ | ✓ | ✓ |
| アカウントが存在する（作成は一切しない） | ✓ | ✓ | ✓ |
| 管理対象としてマークされている | `managed_group` のメンバー | `managed_role` が付与されている（それ以外のロールはなし） | チャネルルール `&tenant-pass:managed` を持つ |
| 管理者権限がない | SUPERUSER、CREATEROLE、CREATEDB、REPLICATION、BYPASSRLS のいずれも、直接 **または祖先ロールのいずれを通じても** 持たない | グローバル権限を一切持たない（すべての `*_priv` 列）、動的権限なし、`mysql`/`sys`/`performance_schema` に対する権限なし、PROXY なし。アカウント **と** 管理対象ロールの両方について | `ACL DRYRUN` により、どのカテゴリやセレクターを通じても管理コマンド（ACL、CONFIG、MODULE、FLUSHALL、FUNCTION LOAD など）を実行できないことを証明する |
| テナント横断のアクセスがない | 定義済みの `pg_*` ロール（例: `pg_read_all_data`）やログインロールのメンバーではない。ADMIN OPTION なし | （グローバル権限は拒否済み） | `ACL DRYRUN` により、ランダムなキーやチャネル（`~*`、`&*`）にアクセスできないことを証明する |
| tenant-pass 自身の管理者アカウントではない | ✓ | ✓ | （マーカー） |

拒否されたアカウントに対しては、クライアントには `403 denied` が返り、監査ログには `account_refused` エラーが記録されます。これはアラートの対象にすべきです。

チェックは、**管理者権限とサーバー全体に及ぶ権限** について意図的に厳しくしています。サーバーレベルで 1 つのアカウント自身のオブジェクトを超えて及ぶもの（スーパーユーザー相当の属性、事前定義ロール、グローバル権限、ワイルドカードのデータベース権限、無制限のキーパターン）は、評価するのではなく拒否します。

このチェックで一般には見えないのは、**他のテナントの** オブジェクトに対する権限付与です（たとえば `GRANT SELECT ON acme.invoices TO t_beta` や、共有テーブルを所有する NOLOGIN グループ）。各テナントの権限をそのテナント自身のデータベース、スキーマ、テーブル、またはキープレフィックスに限ることはプロビジョニング側の役割であり、tenant-pass はそれを前提としています。

## ステートレス性とレプリカ

すべてのレプリカには同じ設定（ローテーション鍵、window、renew_before、ノード名）が必要です。それ以外は何も共有しません。

- 1 つのアカウントに対する並行処理は、ストア（PostgreSQL の `pg_advisory_xact_lock`、MySQL の `GET_LOCK`）によって、またレプリカ内ではプロセス内ロックによって直列化されます。Redis の更新は冪等です。
- 異なるテナント数のレート制限と repair のレート制限はレプリカごとです。レプリカが N 個あれば、実効的な制限値は最大で N 倍になります。
- レプリカを再起動しても何も失われません。

## tenant-pass がしないこと

- 作成、削除、権限付与は一切行いません。テナントとそのアカウントのプロビジョニングは利用者の責任です（そして、別の、より強い権限を持つプロセスで行うべきです）。
- データベースのトラフィックをプロキシしません。
- エンドユーザーを認証しません。それはゲートウェイの役割です。
- 認証情報を保存しません。
