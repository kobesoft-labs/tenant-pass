# 脅威モデル

[English](../en/threat-model.md)

このドキュメントでは、tenant-pass が何を、誰から守るように設計されているのか、そして同じくらい重要なこととして、何を守ら **ない** のかを示します。デプロイする前にお読みください。

## 資産

1. ストア（PostgreSQL、MySQL、Redis）内の **テナントデータ**。
2. **テナントの認証情報**: ウィンドウごとのパスワード。
3. **ローテーション鍵**: これを持つ者は、そこから導出されるすべてのパスワードを計算できます。
4. **ストアの管理者認証情報**: tenant-pass がパスワードを設定するために使うアカウント。
5. **ゲートウェイの署名鍵**: これを持つ者はパスを発行できます。
6. **アプリトークン / クライアント証明書**。

## 信頼の前提

| コンポーネント | 前提 |
| --- | --- |
| tenant-pass のホストとプロセス | 信頼する。ローテーション鍵とストアの管理者認証情報を保持する。 |
| ゲートウェイ | そのテナントについて自身が認証したリクエストに対して **のみ** パスに署名するものと信頼する。 |
| ディレクトリ | テナントを正しいアカウントに対応付けるものと信頼する。（誤りによる被害はストアの安全性チェックで抑えられる。） |
| ストア | パスワードと有効期限を強制するものと信頼する。 |
| ネットワーク | 信頼しない。すべての接続で、証明書とホスト名を検証する TLS を使う。 |
| アプリケーション | **信頼しない。** 侵害されたアプリケーションにできることを制限するのが設計目標である。 |
| 時計 | おおむね同期している（NTP）。ずれは `renew_before` より十分小さくなければならない。 |

## 主要な脅威: 侵害されたアプリケーション

攻撃者がアプリケーションのプロセス内でコードを実行できるようになった場合です（RCE、悪意のある依存関係、盗まれたデプロイ用認証情報など）。

**tenant-pass がない場合**、アプリケーションは通常、すべてのテナントの認証情報（またはそれを復号する鍵）を保持しています。攻撃者はすべてのテナントを即座に読み取れます。

**tenant-pass がある場合**、攻撃者はアプリトークンを手に入れますが、次のようになります。

| 攻撃 | 結果 |
| --- | --- |
| 任意のテナントの認証情報を要求する | 失敗する: パスが必要であり、パスに署名できるのはゲートウェイだけ。 |
| パスを偽造する | 失敗する: アプリケーションはゲートウェイの秘密鍵を持っていない。 |
| 別のアプリケーションから入手したパスを再利用する | 失敗する: `aud` は認証されたアプリケーションと一致しなければならない。 |
| アプリケーションが正規に受け取ったパスを再利用する | 成功するが、それらのテナントに限られ、`exp` まで（数秒）しか使えない。 |
| 同じアプリケーションの他のワーカーが受け取った認証情報を読み取る | そのプロセスのメモリ内に有効な認証情報があるテナント、つまり現在サービス中のテナントに限って成功する。認証情報は 1 ウィンドウ以内に失効する。 |
| 保存されたテナントのパスワードを読み取る | 何も保存されていない。 |
| ゲートウェイに多数のテナントのリクエストを自分へ転送させる | 下記の「ゲートウェイに関する残存リスク」を参照。異なるテナント数のレート制限によって上限が抑えられる。 |
| tenant-pass に管理者アカウントを指させる | アプリケーションからは不可能: アカウントを決めるのはディレクトリであり、ストアは特権アカウントと管理対象外のアカウントを拒否する。 |

したがって、侵害されたアプリケーションによって露出するのは、すべてのテナントが一度にではなく、**攻撃者が居座っている間に実際に使われているテナント** であり、その速度は `limits.max_tenants_per_minute` によって制限されます。検知（監査ログの量、`rate_limited` イベント）によって、対応するための時間を稼げます。

## ゲートウェイに関する残存リスク

パスが証明するのは *「ゲートウェイがこのテナントのリクエストをこのアプリケーションに転送した」* ということだけです。攻撃者が、任意のテナントのリクエストを侵害されたアプリケーションへ転送するようゲートウェイを **仕向ける** ことができれば（たとえば公開ゲートウェイに `Host: victim.example.com` を送るなど）、そのテナントの有効なパスを入手できてしまいます。

このため、ゲートウェイは **そのテナントについてエンドユーザーのセッション（またはジョブ自身の署名付き認可）を認証した後でのみ** パスに署名しなければなりません。認証のないエンドポイント（ログインページ、ヘルスチェック、公開アセット、Webhook）がパスを受け取ってはなりません。[gateway-integration.md](gateway-integration.md) を参照してください。加えて、次の点にも注意してください。

- アプリケーションが内部からゲートウェイに到達できてはなりません（到達できると、任意のホスト名を指定して自分でゲートウェイを呼び出せてしまいます）。これはネットワークレベルで制限してください。
- 異なるテナント数のレート制限によって、この悪用の速度は抑えられます。

ゲートウェイが認証されていないトラフィックに対してパスに署名する場合、tenant-pass の効果は「アプリケーションは、ホスト名を知っている任意のテナントの認証情報を、制限された速度で取得できる」というところまで低下します。それでもパスワードを保存したテーブルよりはましですが、意図された保証ではありません。

## その他の脅威

### tenant-pass の侵害

tenant-pass はローテーション鍵とストアの管理者認証情報を保持しています。tenant-pass が侵害されると **すべての** テナントが露出します。これは tenant-pass がない現状と同じですが、すべてのアプリケーションではなく、1 つの小さなサービスにリスクが集約されます。緩和策は次のとおりです。

- 専用の最小構成のホストまたはコンテナで実行します（distroless イメージ、非 root、読み取り専用のルートファイルシステム、シェルなし）。
- ストアの管理者アカウントには、各ストアガイドに記載された最小権限だけを与えます。
- tenant-pass へのネットワークアクセスを、それを必要とするアプリケーションだけに制限します。
- ローテーション鍵は tenant-pass のシークレットマウントにのみ置きます。

### ローテーション鍵の漏洩

ローテーション鍵を持つ者は、その鍵が有効な過去および未来のすべてのウィンドウについて、そこから導出されるすべてのパスワードを、tenant-pass に接続することなく **オフラインで** 計算できます。ただし、ストアへのネットワークアクセスは依然として必要です。対応: 直ちに鍵をローテーションしてください（[operations.md](operations.md#ローテーション鍵のローテーション) を参照）。1 ウィンドウ後には、古いパスワードはすべて無効になります（PostgreSQL では `VALID UNTIL` により、MySQL/Redis ではスイーパーと発行処理により）。

今後の課題: 鍵を持ち出せないように、HMAC を KMS/HSM に委譲すること。

### ゲートウェイ鍵の漏洩

これを持つ者は、任意のテナント、任意のアプリケーションに対してパスを発行できます。ただし、そのアプリケーションとして認証（アプリトークン / 証明書）する必要は依然としてあります。対応: `gateway_keys` からその鍵を削除し、新しい鍵を展開してください。

### アプリトークンの漏洩

パスがなければ役に立ちません。対応: 設定内のトークンハッシュを置き換えてください。

### ネットワーク上の攻撃者

すべての接続（アプリケーションから tenant-pass、tenant-pass からストアとディレクトリ）は、証明書とホスト名を検証する TLS 1.2 以上を使います。平文にするには 2 つの明示的な設定が必要で、テスト専用です。データベースドライバーは DSN を使わずに設定されるため、ドライバーの安全でないデフォルト値（たとえば libpq の `sslmode=prefer`）が適用されることはありません。

### ストアへの通信中およびストアのログ内のパスワード

tenant-pass が送るのはベリファイア/ハッシュだけです。SCRAM-SHA-256 ベリファイア（PostgreSQL）、`caching_sha2_password` ハッシュ（MySQL）、SHA-256 ACL ハッシュ（Redis）です。これらではログインできません。平文は tenant-pass のメモリ内と API レスポンスの中にしか存在しません。

注意: SCRAM ベリファイアや `caching_sha2_password` ハッシュがあれば、パスワードに対する **オフラインの推測攻撃** は可能です。tenant-pass のパスワードは 256 ビットのランダム値なので、推測は現実的ではありません。それでも、可能であれば管理者ロールについては `log_statement = ddl` やそれに類する設定をオフにしておいてください。

### 時計の操作

各レプリカは書き込みの前に自分の時計をストアサーバーの時計と比較し、差が `rotation.max_clock_skew` を超えると拒否します（`clock_skew`）。したがって、時計が狂ったレプリカがパスワードを未来へ延長したり、アカウントを過去へ戻したりすることはできません。**ストアサーバーの** 時計が狂っている場合、tenant-pass はそれに従います。データベースサーバーでも NTP を実行し、`clock_skew` を監視してください。

### サービス拒否

- ボディは 4 KiB、ヘッダーは 16 KiB に制限されています。読み取り/書き込みのタイムアウトが設定されています。
- 同時リクエスト数は制限されています（`limits.max_concurrent_requests`）。超過したリクエストには即座に `503 busy` が返ります。
- 各リクエストの処理時間は `limits.issue_timeout` で制限されます。
- レディネスプローブの結果は 5 秒間キャッシュされるため、ストアに負荷をかける目的には使えません。
- `repair` による再書き込みは、レプリカごと、アカウントごとに 10 秒に 1 回に制限されています。

tenant-pass はインターネットに公開することを想定して設計されていません。内部ネットワークに配置してください。

## 明示的に目標としないこと

- 侵害された **ゲートウェイ**、**ディレクトリ**、**tenant-pass ホスト**、**ストア** からテナントデータを守ること。
- 侵害されたアプリケーションから、**そのアプリケーションがサービス中の** テナントを守ること。
- 認証済みのアプリケーションから、どのテナントが存在するかを隠すこと（`denied` は「そのようなテナントは存在しない」と「許可されていない」を区別しませんが、タイミングで区別できる可能性があります）。
- ストア内でのテナントアカウント自身の操作から守ること。たとえば、PostgreSQL のロールは自分のパスワードを変更できますが、それによって締め出されるのは、次のウィンドウまたは `repair` までの間、自分自身のテナントだけです。
- データベースレベルの認可を置き換えること。テナントアカウントには、そのテナントのデータに必要な権限（たとえば 1 つのスキーマやデータベースの所有権）だけを与えるべきです。
