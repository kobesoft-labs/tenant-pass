# Contributing

[日本語は下にあります](#コントリビューション)

Thank you for your interest in tenant-pass. Because it is security infrastructure, contributions are held to a high standard. Please read this first.

## Before you start

- **Security issues**: never in public issues or pull requests. See [SECURITY.md](SECURITY.md).
- **Larger changes** (new store types, new API fields, changes to the pass format or derivation): open an issue to discuss the design first. Format and derivation changes need a new version label (`tenant-pass/v2/...`), new test vectors and a migration path.
- **Scope**: tenant-pass deliberately does little. Features that widen its privileges (creating accounts, granting privileges, proxying traffic) are out of scope.

## Development

Requirements: Go (see `go.mod`), Docker (for integration tests).

```sh
go vet ./...
go test -race ./...                  # unit tests
scripts/integration.sh               # starts PostgreSQL, MySQL and Redis in Docker and runs integration tests
go test -run=NONE -fuzz=FuzzVerify -fuzztime=60s ./pass
python3 -I scripts/derivation_vectors.py   # independent reference for the derivation vectors
```

## Rules for code

- Fail closed. If something is unexpected, refuse.
- No secrets in logs, errors returned to clients, panics or metrics. Use `secret.Value` for secrets in memory.
- No new dependencies without discussion; prefer the standard library.
- Every interpolated value in SQL or ACL commands must be generated by tenant-pass or validated against a fixed character set, with a comment saying which.
- Tests for every security check, including the "refuse" path. Store changes need integration tests against real servers.
- Comments explain *why*, especially for security decisions.
- Keep documentation in **both English and Japanese** in sync (`docs/en`, `docs/ja`). If you cannot write one of them, say so in the pull request and maintainers will help.

## Commits and pull requests

- One logical change per pull request, with a description of the motivation and the security impact.
- All CI checks must pass (tests, race detector, vet, staticcheck, govulncheck).
- By contributing, you agree that your contribution is licensed under the Apache License 2.0.

# コントリビューション

tenant-pass に関心を持っていただき、ありがとうございます。セキュリティの基盤となるソフトウェアなので、貢献には高い水準を求めます。最初にお読みください。

## 始める前に

- **セキュリティの問題**は、公開の Issue や Pull Request に書かないでください。[SECURITY.md](SECURITY.md) を参照してください。
- **大きな変更**（新しいストアの種類、API の項目の追加、パスの形式や導出の変更）は、先に Issue で設計を相談してください。形式や導出を変えるには、新しいバージョンのラベル（`tenant-pass/v2/...`）、新しいテストベクトル、移行の手順が必要です。
- **範囲**: tenant-pass はあえて機能を絞っています。権限を広げる機能（アカウントの作成、権限の付与、通信の中継）は対象外です。

## 開発

必要なもの: Go（`go.mod` を参照）、Docker（結合テスト用）。

```sh
go vet ./...
go test -race ./...                  # 単体テスト
scripts/integration.sh               # Docker で PostgreSQL・MySQL・Redis を起動して結合テストを実行
go test -run=NONE -fuzz=FuzzVerify -fuzztime=60s ./pass
python3 -I scripts/derivation_vectors.py   # 導出のテストベクトルの独立した参照実装
```

## コードの決まり

- 迷ったら拒否する（フェイルクローズ）。想定外のことが起きたら断る。
- 秘密の値を、ログ・クライアントに返すエラー・panic・メトリクスに出さない。メモリ上の秘密の値には `secret.Value` を使う。
- 相談なしに依存関係を増やさない。標準ライブラリを優先する。
- SQL や ACL のコマンドに埋め込む値は、tenant-pass が生成した値か、固定の文字の集合で検証した値に限る。どちらなのかをコメントに書く。
- すべての安全確認に、「拒否する」場合を含めてテストを書く。ストアの変更には、実際のサーバーでの結合テストが必要。
- コメントには「なぜそうするか」を書く。特にセキュリティ上の判断について。
- ドキュメントは **英語と日本語の両方**（`docs/en`、`docs/ja`）を揃える。どちらかが書けない場合は Pull Request にその旨を書いてください。メンテナーが手伝います。

## コミットと Pull Request

- 1 つの Pull Request には 1 つのまとまった変更を入れ、動機とセキュリティへの影響を説明してください。
- CI（テスト、race detector、vet、staticcheck、govulncheck）がすべて通ること。
- 貢献したコードは Apache License 2.0 で提供されることに同意したものとみなします。
